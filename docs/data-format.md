# Data format (spike, v0)

The objects Bowei's server stores and returns. The HTTP surface that moves them
is in [`api.md`](api.md). Both are the contract the extensions wire against;
change them here first.

Scope: the build-night demo loop (record, send, notice, watch, reply, pick).
Sign-in, invites, and per-circle permissions are out of scope. The circle is a
hard-coded list of people, each with a fixed token.

## Conventions

- **JSON, camelCase**, UTF-8. Field names match the existing studio code where
  one exists (`anchor` there is `anchorSec` here, `syncMode` and `kind` keep
  their values).
- **Times in the base video**: seconds, as a JSON number with millisecond
  precision (`83.417`). Same unit as `HTMLMediaElement.currentTime`.
- **Wall-clock times**: ISO 8601 UTC strings (`2026-10-08T21:14:03.512Z`).
  Server-set fields are authoritative. Fields named `client*` carry the
  browser's clock, kept only for debugging (clock skew, offline queues).
- **IDs are UUIDv4 strings generated by the client** for everything the client
  creates (media, reactions, sends). Creates are `PUT /…/{id}`, so a retry after
  a dropped connection can never make a duplicate. The server generates ids
  only for its own records (events, requests, links).
- **Nothing is hard-deleted.** Deletes set `deletedAt`. Uploaded bytes are never
  modified; any later transcode is stored beside the original.
- Unknown fields sent by a client are ignored on input but kept in the event
  log's raw body (see [Debug metadata](#debug-metadata)), so a client can ship a
  field before the server knows it.

## Person

Someone in the circle. Hard-coded on the server for the spike.

```jsonc
{
  "id": "bowei",                 // short slug, stable
  "displayName": "Bowei",
  "role": "owner",               // "owner" | "friend" | "creator"
  "color": "#d9480f",            // marker / chip colour
  "avatarUrl": null              // null: clients draw initials on `color`
}
```

Server-only (never returned): `token`, the bearer token that identifies this
person (see `api.md`, Identity).

## Video

What a reaction is attached to. The server keeps one row per video so the
"From your circle" shelf can render without calling YouTube.

```jsonc
{
  "ref": "yt:dQw4w9WgXcQ",       // the key; see below
  "source": "youtube",
  "youtubeId": "dQw4w9WgXcQ",
  "title": "Never Gonna Give You Up",
  "channelName": "Rick Astley",
  "channelId": "UCuAXFkgsw1L7xaCfnd5JJOw",   // null if the client couldn't read it
  "channelUrl": "https://www.youtube.com/@RickAstleyYT",
  "durationSec": 212.091,         // null if unknown (feed cards don't expose it)
  "thumbnailUrl": "https://i.ytimg.com/vi/dQw4w9WgXcQ/hqdefault.jpg",
  "firstSeenAt": "2026-10-08T21:10:00.000Z",
  "lastSeenAt":  "2026-10-08T21:14:03.512Z"
}
```

- **`ref`** is `<scheme>:<id>`. The spike only uses `yt:<11-char YouTube id>`.
  The scheme exists so a later audio-fingerprint id (`fp:…`) can name "the same
  video" across copies without a format change. Clients must treat `ref` as
  opaque apart from building it from a YouTube id.
- Clients never create a Video directly. Every write that names a video carries
  a `video` object (any subset of the fields above, plus `ref`); the server
  upserts it, keeping the latest non-null value of each field.

## Media

One uploaded file: a reaction recording, or an optional poster frame.

```jsonc
{
  "id": "6f1c0c1e-2b0e-4a57-9a3b-6a0f6a1d8f10",
  "url": "https://<server>/media/6f1c0c1e-2b0e-4a57-9a3b-6a0f6a1d8f10",
  "mimeType": "video/webm;codecs=vp8,opus",  // exactly what MediaRecorder reported
  "sizeBytes": 1843221,
  "sha256": "9b1f…",
  "uploaderId": "bowei",
  "createdAt": "2026-10-08T21:14:02.900Z",
  "probe": {                      // server's own read of the file; null if no probe ran
    "container": "webm",
    "durationSec": 11.84,         // null when the file has no duration header (Chrome webm)
    "hasVideo": true,
    "hasAudio": true,
    "width": 640,
    "height": 480
  }
}
```

- `url` is a capability URL: anyone holding it can play the file, no token. A
  `<video src>` cannot send an auth header, so this is what makes playback in a
  content script simple. The id is a random UUID, so it isn't guessable.
- Chrome's MediaRecorder writes webm with no duration, which makes seeking
  unreliable. The client's measured `durationSec` on the reaction is the source
  of truth; `probe.durationSec` is for cross-checking.

## Reaction

One take, anchored to a moment of one video.

```jsonc
{
  "id": "a3e9…",
  "videoRef": "yt:dQw4w9WgXcQ",
  "authorId": "bowei",
  "kind": "video",                // "video" | "audio" | "text"
  "syncMode": "playing",          // "playing" | "paused"
  "anchorSec": 83.417,            // base-video time the reaction starts at
  "durationSec": 11.84,           // video/audio: recording length; text: how long to show it
  "text": null,                   // text body for kind "text"; optional caption otherwise
  "mediaId": "6f1c…",             // required for video/audio, null for text
  "posterMediaId": null,          // optional still (image/jpeg) for shelf previews
  "replyToReactionId": null,      // set when this answers someone else's reaction
  "createdAt": "2026-10-08T21:14:03.512Z",
  "updatedAt": "2026-10-08T21:14:03.512Z",
  "deletedAt": null,
  "capture": { /* CaptureInfo, see Debug metadata */ }
}
```

Read responses also embed `author` (a Person) and `media` / `posterMedia`
(Media objects) so a client needs one call to render and play a reaction.

### Playback meaning

This is the rule both extensions implement. The server only stores it.

- **`syncMode: "playing"`** (over the video): while the base video plays through
  `[anchorSec, anchorSec + durationSec)`, the reaction plays with
  `reaction.currentTime = base.currentTime - anchorSec`, at the base video's
  playback rate. Pause, seek, and rate on the base video carry over.
- **`syncMode: "paused"`** (on a paused frame): when the base video reaches
  `anchorSec`, the viewer's player pauses, the reaction plays from 0 for
  `durationSec`, then the base video resumes. Skip resumes immediately.
- **Text** uses the same two modes. `durationSec` is the time on screen; clients
  default it to `clamp(2 + 0.35 * wordCount, 3, 10)` seconds.

Only a reaction's author can change it, and only `anchorSec`, `syncMode`,
`text`, and `capture.anchorNudges` (the nudge and fix-up controls). Changing
the recording means a new take with a new id.

### Drafts never reach the server

Recording and Retake stay in the browser. A reaction is uploaded only on
**Keep**. The studio's IndexedDB becomes a draft store plus an offline queue for
Keeps that haven't uploaded yet.

## Send

The one sharing object. Bowei sending his reactions to his wife, and his wife
sending Bowei a pick, are both Sends.

```jsonc
{
  "id": "c41d…",
  "senderId": "bowei",
  "videoRef": "yt:dQw4w9WgXcQ",
  "reactionIds": ["a3e9…", "b710…"],   // may be empty: a bare pick with a note
  "note": "the bridge at 1:23, you'll see",
  "recipients": [
    {
      "personId": "wife",
      "openedAt": null,          // first time they landed on the video from this send
      "watchedAt": null,         // they played it through (see api.md, flow 5)
      "dismissedAt": null        // removed from their shelf without watching
    }
  ],
  "replyToSendId": null,         // set on a send that answers another send
  "origin": "watch_page",        // "watch_page" | "feed_card" | "react_back" | "creator_page"
  "createdAt": "2026-10-08T21:15:40.004Z",
  "client": { /* ClientInfo, see Debug metadata */ }
}
```

- A send is immutable apart from the recipients' state timestamps. Sharing more
  reactions later is a new send.
- Every id in `reactionIds` must be authored by the sender, on the same video,
  and not deleted.
- Read responses embed `sender`, `video`, and the full `reactions` (each with
  `author` and `media`). A reaction deleted after sending drops out of
  `reactions` but stays in `reactionIds`.
- Stretch: a send made with a creator link also carries
  `links: [{ "token", "url", "createdAt" }]` (`api.md`, flow 9).

### Who can see a reaction

A person sees a reaction if **they wrote it**, or it is in **a send addressed to
them**. Nothing else. That is the whole visibility rule for the spike, and it is
what makes the send sheet's tick-boxes mean something. A reply becomes visible
to the original sender because "React back" ends in a send to them (flow 6 in
`api.md`).

## Debug metadata

What the server keeps beyond the product data, so that when a reaction plays out
of sync or a send goes missing at the demo, the cause can be found from the
server alone.

### On every request

Clients send:

| Header | Example | Why |
|---|---|---|
| `X-Client` | `yt-reaction-studio/20261009032303-7e10d7a7` | which extension and which build hash made the call |
| `X-Client-Session` | a UUID made once per page load | groups one page's calls and telemetry together |

The server returns `X-Request-Id` and `X-Server-Build` on every response,
includes `requestId` in every error body, and appends one row per request to
the request log: request id, time, person, method, path, status, latency,
`X-Client`, `X-Client-Session`, user agent, request and response sizes.

### ClientInfo (on every created object)

```jsonc
{
  "clientBuild": "yt-reaction-studio/20261009032303-7e10d7a7",
  "clientSession": "e3b0…",
  "clientCreatedAt": "2026-10-08T21:14:03.100Z",
  "userAgent": "Mozilla/5.0 … Firefox/133.0",
  "pageUrl": "https://www.youtube.com/watch?v=dQw4w9WgXcQ&t=80s"
}
```

### CaptureInfo (on every reaction)

ClientInfo plus how the take was made. The base-video snapshots at start and
stop are the important part: for a "playing" reaction the base video should
have advanced by about `durationSec`. If it didn't, an ad, a seek, or a buffer
stall happened mid-recording, and that explains later drift.

```jsonc
{
  "...ClientInfo": "…",
  "recordStartedAt": "2026-10-08T21:13:50.010Z",   // client clock
  "recordStoppedAt": "2026-10-08T21:14:01.860Z",
  "baseAtStart": { "currentTimeSec": 83.417, "paused": false, "playbackRate": 1, "adShowing": false, "durationSec": 212.091 },
  "baseAtStop":  { "currentTimeSec": 95.240, "paused": false, "playbackRate": 1, "adShowing": false, "durationSec": 212.091 },
  "anchorOriginalSec": 83.417,     // before any nudges
  "anchorNudges": [-1, -1],        // in order; anchorSec = original + sum
  "retakesBefore": 2,              // discarded takes before this Keep
  "recorder": {
    "mimeType": "video/webm;codecs=vp8,opus",
    "timesliceMs": 1000,
    "chunkCount": 12
  },
  "devices": { "camera": "FaceTime HD Camera", "microphone": "MacBook Pro Microphone" },
  "track": { "width": 640, "height": 480, "frameRate": 30 }
}
```

All fields are optional for the server; send what's available.

### Event log

Append-only. Two sources, one table:

- **Server events**: every successful write, with the person, request id, and
  the raw request body as received (`media.uploaded`, `reaction.created`,
  `reaction.updated`, `reaction.deleted`, `send.created`,
  `send.recipient_state`).
- **Client telemetry**: what happened in the browser, posted in batches
  (`api.md`, Telemetry). Playback is what most needs explaining after a demo.

```jsonc
{
  "id": "srv-generated",
  "receivedAt": "2026-10-08T21:16:10.120Z",
  "source": "client",                 // "server" | "client"
  "type": "reaction.drift_corrected",
  "personId": "wife",
  "requestId": "…",
  "clientBuild": "…", "clientSession": "…", "clientAt": "…",
  "videoRef": "yt:dQw4w9WgXcQ",       // when relevant
  "reactionId": "a3e9…",              // when relevant
  "sendId": null,
  "data": { "driftSec": 0.42, "baseTimeSec": 88.1 }
}
```

Client event types the extensions should emit:

| Type | `data` |
|---|---|
| `watch.loaded` | `{ visibleReactionCount }`, when a watch page has fetched its reactions |
| `reaction.started` | `{ baseTimeSec, syncMode }` |
| `reaction.finished` | `{ baseTimeSec, playedSec }` |
| `reaction.skipped` | `{ baseTimeSec, playedSec }` |
| `reaction.drift_corrected` | `{ driftSec, baseTimeSec }`, each re-seek of the reaction player |
| `reaction.media_error` | `{ code, message }`, from the `<video>`/`<audio>` error event |
| `upload.retry` | `{ attempt, status, error }` |
| `error` | `{ message, stack, where }`, any caught exception worth keeping |

### Debug page

`GET /debug` on the server (see `api.md`) shows all of the above: people,
videos, reactions with inline players, sends with recipient states, and the
latest requests and events, each row expandable to its raw JSON.
